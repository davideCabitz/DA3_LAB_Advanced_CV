## Phase 3 — What LoRA actually does inside DA3, step by step

Explain with the **real module names from `src/da3/`** (verify them in the code, do not invent):
1. The math: for a frozen linear layer `W`, `W' = W + (alpha / r) * B A`, `A` random init, `B = 0` →
   at step 0 the model is exactly the released DA3. Rank `r`, `alpha`, dropout, and the number of
   trainable parameters for DA3-Small and DA3-Base.
2. **Where** the adapters go: which linear layers (qkv, attention proj, MLP fc1/fc2) in which blocks;
   within-view (`L_s`) vs cross-view (`L_g`) blocks; blocks 4–11 as proposed in the report; whether the
   camera encoder `E_c`, camera head `D_C` and the Dual-DPT head are frozen, LoRA-ed or trained; why.
3. The **forward pass** with the weights: images → patch embedding → camera tokens (learned token or
   `E_c(f, q, t)`) → within-view / cross-view attention via token reordering with the LoRA deltas added →
   Dual-DPT (depth + conf, ray + conf) → camera head; then P = t + D·d and pose from rays (Eq. 1–2).
4. The **training step**: teacher pass (frozen, e.g. pose-conditioned DA3), student pass (unposed + LoRA),
   which losses from `src/da3/losses/` are used and on which outputs, GT/scale normalisation, anchor to
   frozen outputs against forgetting, backward pass **only** into `A`/`B`, optimiser and schedule.
5. **Inference**: adapter on/off switch, merge into `W` for zero overhead, saving only the adapter weights,
   and the bit-exact "LoRA off" test.

## Phase 4 — Pre-registered statistical comparison on all fundamental benchmarks (mandatory)

Write `docs/LORA_ANALYSIS_PLAN.md` + `configs/lora_analysis.yaml` **before** any result is seen, in the
style of `docs/FOVEATED_ANALYSIS_PLAN.md` (constants frozen, deviations logged with date). The comparison
is **released DA3 vs DA3 + LoRA**, same weights, same model size, same protocol, and must cover **every
fundamental benchmark of the paper (Sec. 6)** that is feasible:
- **Pose**: AUC@3 and AUC@30 on HiRoom, ETH3D, DTU, 7Scenes, ScanNet++ (up to 100 images/scene, fixed seed).
- **Reconstruction**: evo + RANSAC alignment, TSDF fusion with the paper's voxel sizes, Chamfer distance
  and F1 (0.05 m HiRoom / 7Scenes / ScanNet++, 0.25 m ETH3D).
- **Monocular depth**: the paper's monocular table (AbsRel, δ1), if a loader exists or can be added.
- **NVS** (PSNR / SSIM / LPIPS on DL3DV, Tanks and Temples, MegaDepth): only if a GS head exists; if not,
  mark it "not evaluated" with the reason. Never report a number that was not computed.
- **In-domain target** of the LoRA (e.g. held-out KITTI drives for E3): ATE / RPE and AbsRel vs LiDAR.

The statistics must be theoretically correct:
- Unit of analysis = **scene**; **paired** design (identical scenes, frames, frame order, resolution and
  seeds for both arms). Training seeds: 2–3 LoRA runs; analyse the per-scene difference averaged over
  seeds and also report the between-seed spread (seed variance must not be confused with improvement).
- Per benchmark × metric: mean paired difference with **scene-level (cluster) bootstrap 95% CI**
  (≥10k resamples, fixed seed) and a paired test (Wilcoxon signed-rank or sign-flip permutation);
  effect size; justify the test choice given small n (e.g. 7 scenes on 7Scenes).
- **Multiplicity**: one primary endpoint (pre-declared), the rest secondary with Holm–Bonferroni
  (or a hierarchical/gatekeeping order), declared in the plan.
- **Non-inferiority** for the "no regression on Sec. 6" claim, with margins fixed in advance per metric.
- Report the paper's dataset-level aggregate as well, so numbers stay comparable to Tab. 2/3, with the
  setting tags **[paper]**, **[official]**, **[official+LoRA]**.
- Leakage check: LoRA training scenes disjoint from every test scene; state it in the record.
- Every run saved as a `da3-result/1` record (config, seed, commit hash, metrics) under
  `experiments/results/lora/`, and included in `09_compare_all`.
